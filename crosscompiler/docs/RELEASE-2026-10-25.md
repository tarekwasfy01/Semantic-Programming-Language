## What changed in the native Windows graph

- Signed 64-bit `integer.divide` and `integer.remainder` lower through the
  existing native x64 code-emission path.
- The reader checks the flat explicit operation type rather than accepting
  `signed` and `bits` values elsewhere on the node line. Ambiguous nested
  objects before the type are rejected fail-closed.
- `compile_file` checks all eight `sys_mmap` results before using the allocated
  areas; `0` and `-1` return compile error 3 instead of being dereferenced.

## Validation performed before publication

- Native fixtures: signed `72 / 3` exited 24; remainder exited 1; `return42`
  exited 42; tuple/index exited 35; BindingPattern exited 42.
- Unsigned, signed-32, extra-field, and nested-decoy division types were
  rejected at compile time.
- Direct-SE Stage1, Stage2, and Stage3 were 245,248 bytes and SHA-identical to
  the executable above.
- The local active `swc.smod --embed-all` build produced the same SHA.
- After copying into this repository, its `bin/swc.exe` compiled the published
  relative-path `manifests/swc.smod` with `--embed-all` to Stage2; Stage2
  compiled the same manifest to Stage3. Both returned exit 0. Both outputs
  were 245,248 bytes with SHA-256
  `B0BF89D75BA534A523EF618D7E3A0BF6B4B1AC607409E710E699B2022CD59845`,
  matching the checked-in executable. The manifest's source size and hash
  matched the checked-in SE file.

## Known limits

An earlier large-graph candidate sporadically exited with Windows access
violation `0xC0000005`. This update's allocation guards are a real safety
improvement, but the failing allocation case was not injected and the root
cause of the intermittent crash is not proven. Successful byte-identical
selfhosting does not establish complete stability or complete UAST coverage.
