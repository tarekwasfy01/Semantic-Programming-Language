Module System

Das Semantic-Modulsystem löst verschiedene Artefaktarten über eine gemeinsame Grenze auf: Quellen, Semantic-Dateien, Pakete, native Objekte und Binärdateien werden zu kanonischen Semantic-Programmen.

Wichtig: Der Resolver startet keinen fremden Compiler. Go, Python, Rust, C, C#, Java und weitere Sprachen werden intern über ihr Frontend und LowerSource semantisch abgesenkt.

Eine universelle Importgrenze

UniversalModuleResolver erkennt den Artefakttyp oder übernimmt eine explizite Sprache. Danach liegt das Ergebnis als SemanticModule mit UAST, Ursprung, Symbolen, Contracts und Dependencies vor.

  • .se Semantic-Quellmodul
  • .sp Semantic-Transport
  • .spz kanonischer Semantic-Payload
  • Go, Python, Rust, C/C++, C#, Java, Kotlin, Nim, Swift, Zig und weitere Quellen
  • Assembly sowie PE/COFF- und andere native Artefakte

Auto-Transpile-Import

„Auto-Transpile“ bedeutet keine reine Textübersetzung. Das interne Frontend liest die Ursprungssprache und erzeugt daraus direkt die gemeinsame Semantic-Repräsentation.

Quelle oder Paket  →  DetectArtifact / --language  →  LowerSource(...)  →  SemanticProgram + UniversalAST + Origin.Modules  →  SemanticModule  →  SPZ / SE / SMod

Bei Go werden Modulpfade aus go.mod normalisiert. Explizite externe Pakete können als pkg:go:... gekennzeichnet werden. Der Resolver prüft zuerst den lokalen Semantic-Store und verwendet erst bei einem Cache-Miss lokale Quellen, Archive oder Registry-Adapter.

SMod-Pakete

.smod ist ein datenbasiertes Paketmanifest, kein zweites AST-Format. Es beschreibt Paketidentität und Semantic-ready Einheiten.

{ "name":"paket", "module_path":"example.org/paket", "package_hash":"...", "files":[{ "path":"src/file.go", "semantic_path":"semantic/src/file.go.spz", "readable_semantic_path":"semantic/src/file.go.se", "source_hash":"...", "symbols":["paket.Function"], "status":"SEMANTIC_READY" }] }

Der Projektlinker kann dadurch genau passende Einheiten laden, ohne jedes Paket erneut zu scannen oder zu transpilieren.

Cache-Modell

Module werden content-addressed gespeichert. Der Cache-Key bindet Quellhash, Frontend-/Schema-Version, Semantic-Root, Dependencies und Contracts.

%LOCALAPPDATA%\Semantic\Modules  ·  index  ·  cache  ·  modules  ·  locks  ·  download  |  module.spz  ·  module.se  ·  module.meta

Embedding und Linking

Abhängige Module werden nicht blind in jede Einheit kopiert. Es gibt inline (Payload einmal enthalten), reference (Owner-Verweis) und external (bewusst ungelöstes externes Modul).

Für Projekte gibt es references, needed und all. all materialisiert die vollständige deklarierte Modul-Closure und ist der relevante Modus für den Selfhost-Fullbuild.

Native Module

.obj, .exe und .dll werden analysiert und mit Architektur- und ABI-Fakten geführt. Wenn kein verlustfreies Lifting möglich ist, bleibt das Artefakt als explizites NATIVE_EXTERNAL-Modul erhalten.

Warum Modulidentität für Selfhosting zählt

Native Selfhosting ist mehr als einzelne Funktionsbytes. Cross-Unit-Aufrufe, Globals, Layouts, Symbolnamen und Semantic-Identitäten müssen gemeinsam stimmen.

Quelle / .se  →  interne Frontends  →  Semantic-Einheiten + SMod  →  projektweiter Index  →  SemanticModulesAll  →  OBJ mit Symbolen und Relocations  →  Semantic-Linker → EXE / ELF
